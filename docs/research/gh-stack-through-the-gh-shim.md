# Does `gh stack` survive the board's `gh` shim? (gh#324)

Measured on the box, 2026-08-11, against `gh-stack v0.1.0` and the live shim
generated by `comet-board` 0.3.7. This blocks gh#287, which cannot be shaped
until it is known whether stacked PRs are a feature or a shim rewrite.

## Answer

**It works today, unchanged.** Argv survives verbatim, the extension
authenticates with the shim-minted installation token, and one mint covers a
whole verb including its `git push`. gh#287 can be shaped as written: a feature
that runs `gh stack`, with no change to `git_credentials.rs`.

The one thing gh#287 does have to carry is an **install step** — the extension
is box-level and per-box, not per-run, and today only the box has it.

## What was measured

The rig reproduced a dispatch rather than approximating one:

- The `gh` shim was generated from `gh_shim_script`'s own template and
  `diff`ed against the live `~/.comet-native/board/state/bin/gh` — identical
  but for the board path, which was pointed at a logging wrapper so every mint
  could be counted. The askpass shim was `askpass_shim_script` verbatim.
- The environment was `agent_env` and nothing else, under `env -i`: no
  inherited `GH_TOKEN`, no login shell, no ambient anything.
- **`GH_CONFIG_DIR` was pointed at an empty directory.** This is the load-bearing
  control. The box has a real `gh auth login` (a `gho_` token for
  `bredebjorhovd`) in `~/.config/gh/hosts.yml`, and any test that left it
  reachable would have proved nothing about a fresh box. With an empty config
  dir, `gh` has zero known hosts and the minted token is the only credential in
  the world.

### 1. Argv survives, verbatim

The shim's last line is `exec '<gh>' "$@"`, and `"$@"` is the one form that
neither splits nor globs. Against an argv recorder standing in for the real
`gh`:

```
$ gh stack submit --json --title "a title with spaces" --draft -- --literal "quote's"
argc=9
argv[1]=<stack>     argv[2]=<submit>   argv[3]=<--json>
argv[4]=<--title>   argv[5]=<a title with spaces>
argv[6]=<--draft>   argv[7]=<-->
argv[8]=<--literal> argv[9]=<quote's>
```

Nine arguments in, nine out: embedded spaces intact, `--` intact, an
apostrophe through a shell that quotes with apostrophes intact. There is no
subcommand mangling to worry about, and there was never a mechanism for one —
the shim does not parse its arguments, it forwards them.

### 2. The extension authenticates with the minted token

`gh` runs an extension as its own process, so the question is whether that
child inherits the credential. It does, and the proof does not involve `gh` at
all — the extension binary was invoked **directly**, twice, same command, same
working tree, with only `GH_TOKEN` differing:

```
$ gh-stack checkout 323                      # no token
✗ failed to create GitHub client: determining repository: unable to determine
  current repository, none of the git remotes configured for this repository
  point to a known GitHub host

$ GH_TOKEN=<minted> gh-stack checkout 323    # the shim's token
✗ PR #323 is not part of a stack on GitHub
```

The second is a real answer from the API about a real PR. The extension is a Go
binary carrying `GH_TOKEN` / `GITHUB_TOKEN` / `GH_ENTERPRISE_TOKEN` (go-gh's
own resolution), and the shim exports `GH_TOKEN` into the process it execs, so
the extension inherits it like any other child.

Through the shim end to end, on a config dir with no login in it:

```
$ gh auth status
  ✓ Logged in to github.com account comet-board[bot] (GH_TOKEN)
```

`comet-board[bot]` — the App installation, not the box's `bredebjorhovd`.

### 3. One mint is enough for a multi-call verb

Every invocation minted **exactly once**, with no exceptions across
`--help`, `view`, `view --json`, `init`, `checkout`, `push`, `extension
install` and two `gh api` calls. The extension does not re-enter `gh`, so there
is no second trip through the shim: one `gh stack submit` is one process tree
holding one token.

That token is good for an hour (`exp - iat = 3600` in the JWT-bearing form), so
"one mint per verb" is only a problem for a `submit` that runs longer than an
hour, which is not a thing.

**Note for whoever reads a mint next.** GitHub returns installation tokens in
two formats, apparently at random from call to call:

```
mint 1: 383 chars   ghs_<installation-id>_<JWT>   (ver 3, issuer "authnd")
mint 2:  40 chars   ghs_<36 chars>
```

Both authenticate; both are one hour. A 383-character `GH_TOKEN` is not a
mangled token and not a shim bug — it is the newer format with a JWT in it.
Anything that sanity-checks a minted token by its length will be wrong half the
time.

### 4. The push half works under the real remote

`gh stack push` and `gh stack submit` shell out to `git push`, which is the
askpass path rather than the `gh` path. Tested twice, because the scratch clone
and a real dispatch differ:

| remote | result |
| --- | --- |
| `https://x-access-token@github.com/…` (what `clone_urls` hands `git clone`) | pushed |
| `https://github.com/…` (**what a real checkout holds** — `~/.comet-native/repos/comet-board`) | pushed |

The second is the case that mattered. With no username in the URL, git asks for
one first, and `askpass` answers `x-access-token` before answering the password
prompt with a token. Both prompts, one helper, no terminal — it works, and it
is the configuration every dispatched agent is actually in.

A scratch branch was pushed and deleted for each; no PRs were created, and no
`gh324-*` branches remain on the remote. Nothing in `.github/workflows/` fires
on a non-`main` branch push, so nothing was woken up.

## Where the extension lives

**`~/.local/share/gh/extensions/gh-stack/`** — the XDG *data* dir, not the
config dir. Three consequences:

- It is **box-level and shared**: every dispatched agent on the box sees the
  same copy. It is not per-run. `CODEX_HOME` / `CLAUDE_CONFIG_DIR` are harness
  config dirs and have no bearing on `gh`; `AgentAccounts::materialize` does not
  touch it, and nothing in the engine sets `HOME` or `XDG_DATA_HOME` for a child.
- `GH_CONFIG_DIR` does **not** move it — that only moves `hosts.yml` and
  `config.yml`. Only `XDG_DATA_HOME` would.
- Installing it is a **one-time per-box** act, and a box that has not had it
  done gets `unknown command "stack" for "gh"`. As of this writing the Hetzner
  box has it (installed by this experiment, exit 0, through the shim, on the
  minted token — so `gh extension install` needs no human login either).

## What would have had to change, and did not

Nothing. For the record, in case a future `gh` or extension breaks it:

- The shim forwards argv with `"$@"` and execs; there is no parsing to fix.
- It exports `GH_TOKEN` into the process it execs, so anything `gh` spawns
  inherits it — extensions included.
- The shim directory is *prepended* to PATH (`prepend_dirs_to_path`), so an
  extension that shelled out to `gh` would find the shim and re-mint rather
  than reach `/usr/bin/gh` unauthenticated. gh-stack does not, but it would be
  safe if it did.

The failure mode to watch is an extension that reads `~/.config/gh/hosts.yml`
directly instead of going through go-gh's auth resolution. That extension would
work on the box (which has a login) and fail on a fresh one. gh-stack is not
such an extension.
